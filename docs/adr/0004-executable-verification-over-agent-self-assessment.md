# ADR 0004: Executable Verification Over Agent Self-Assessment

## Status
Accepted

## Context
A major failure mode in autonomous coding and architecture systems is trusting the generating agent's self-assessment ("I have completed the task and verified all edge cases"). Self-assessment is prone to confirmation bias, skipped checks, and false positives.

`AGENTS.md` and `.agents/rules/verification.md` explicitly mandate: "Agent says done is not completion." A task or implementation is complete only when its acceptance criteria are mechanically verified through automated checks and executable evidence.

## Decision
Every architecture decision and invariant generated by ArchitectAI must produce executable verification specifications (`VerificationSpec`) and testable contracts (`EngineeringContract`).

Specifically:
1. `VerificationSpec` defines:
   - Target property or invariant being verified.
   - Preconditions and environment setup.
   - Action / stimulus applied to the system.
   - Measurable expected outcome or property.
   - Concrete evidence required (e.g., test output, exit code, metric threshold).
   - Whether the verification is automatable in CI/CD.
2. Acceptance gates are strictly mechanical:
   - Typechecking passes without exceptions.
   - Unit tests pass.
   - Architectural boundary tests pass.
   - Artifacts validate against runtime schemas (Zod).
3. The verification runner executes independently of the generating agent and reports factual results.

## Consequences
### Positive
- Prevents premature declarations of completion.
- Guarantees that architectural boundaries and invariants are continuously enforced.
- Creates regression-safe boundaries that survive model updates.

### Negative / Tradeoffs
- Writing comprehensive verification specs requires more upfront design effort than freeform code generation.
- Non-automatable specs (e.g., manual exploratory security testing) must be explicitly flagged and cannot automatically pass CI gates.
